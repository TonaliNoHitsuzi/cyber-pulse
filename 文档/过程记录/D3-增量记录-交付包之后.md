## 一、老方法加固（先保证不退化）

### 问题｜BPM 偶发显示 `-1`
- **现象**：恢复老方法后，悬空或弱信号时出现 `-1`
- **根因**：`intervals[]` 是固定 9 长度环形数组，新间隔插在**尾部**，取值却复制**前 n_iv 个**；
  有效区间少时复制到的全是初始 0 → `60000 / 0`（浮点除零 → 未定义行为）
- **解决**：统一取尾部 `intervals + (BPM_MED_N - n_iv)`
- **结果**：悬空 10 秒全程 `bpm=0`；按压 23 秒 **恒 78 BPM、σ=0.0、GOOD 93%**（历史最佳）

## 二、运动模式算法（设计与仿真，未上板）

### 2.1 仿真发现的两个硬事实
1. **噪声底随耦合漂移**：好耦合段 p50≈60、悬空段 p50≈8~12。
   固定阈值 40 在噪声高的录音里会把噪声全当峰——这正是老数据"周期规律怪"的来源
2. **真实波形不是等间距双峰**：每拍是一个 200~320 的大包络（含重搏波），拍间是 40~80 的噪声底

### 2.2 关键证据：为什么高心率必须换配对方式
| 场景 | 真拍保留率 | i+2 中位 | 得出 BPM | 真值 |
|---|---|---|---|---|
| 理想 80 | 102% | 1120ms | 54 | 80 |
| 理想 150 | 100% | 800ms | **75** | 150 |
| 纹波 150 | 100% | 800ms | **75** | 150 |

→ 心率高时重搏波与主峰融合，i+2 跨两拍，直接给出半值。**必须动态配对**

### 2.3 四级演进
1. 固定阈值 + i+2 中值（出厂，已验证）
2. SNR 自适应阈值 + 相位锁定 + 卡尔曼
3. 协方差导出的搜索窗口（σ 含速度项）+ 绝对伪迹门
4. **贝叶斯融合**：先验（KF 预测）× 似然（幅度 × NCC 形态）→ 后验 argmax，R 由后验曲率自动得出

### 2.4 外部建议（Kimi）的落地
| 建议 | 采纳 | 实现 |
|---|---|---|
| 二阶 CV 模型（含速度） | ✅ | 状态 [hr, v] |
| Q 留裕量 | ✅ | σ_a = 3 BPM/s² |
| 新息监测 + 动态 Q | ✅ | NIS 的 EMA → 放大 P（衰减记忆） |
| Mahalanobis 门控 | ✅ | 与生理绝对门（45 BPM/拍）并用 |
| R 随信号质量变化 | ✅ | `R += 25(1−sc)² + 12(1−p95/120)²` |
| 模式自适应 Q | ✅ | 无 IMU，用自身速度：`σ_a=1.5+2.5·min(1,|v|/5)` |
| IMM / 粒子滤波 | ⏸ 不做 | 收益不抵复杂度 |

### 2.5 仿真结果（12 个独立种子，中位 MAE）
| 轨迹 | 基线 | 自适应版 |
|---|---|---|
| 指数上升 τ=5s | 2.4 | 4.3 |
| 线性上升 80→160/20s | 9.8 | 8.9 |
| 冲刺循环 90↔170 | 5.1 | 9.1 |
| 双段变速 | 23.0 | **10.8** |
| 阶跃↓（骤减速） | 58.5 | **27.3** |
| 随机游走 | 69.5 | **19.9** |
| 阶跃↑ | 23.4 | 41.8 |
| 正弦 100±30 | 6.5 | 7.7 |

平均 23.1 → **20.9**；改善集中在"减速/随机游走"，代价是"阶跃上升"。
**结论：瓶颈不在 Q/R 调参，而在"哪个峰才是这一拍"** → 模板匹配是治本方向

## 附3：D4 下午——悬空假阳性 78 BPM 问题（射频串扰）

### 问题｜悬空状态下蓝牙连接后 BPM 显示 78，偶尔空白
- **现象**：传感器全程悬空（无接触），BLE 连接时手机 App 显示 BPM=78，偶尔掉到 0
- **定位**：串口日志显示正常连接时悬空干净（p50=5-13, bpm=0）；
  但在 BLE 断线→重连→补发突发期间 p50 被抬到 18-20（质量门边缘）
- **根因**：**补发突发的密集射频**（重连后 20 批/秒 × 202 字节 ≈ 4KB/s，是正常流量的 10 倍）
  耦合到压电膜 GΩ 级高阻节点，把信号底噪抬到质量门阈值附近，偶尔越过就放行伪迹峰
- **解决**：补发期间（`replay_pending=1`）临时把 p50 质量门从 18 收紧到 30
- **验证**：
  | 测试 | 结果 |
  |---|---|
  | 悬空 + 3 轮断连重连 | 57 帧，零假阳性，不复发 ✅ |
  | 按压 + 收紧门固件 | 35/38 帧出数，BPM 中位 77 (74~79)，p50 最高 44 远超 30 ✅ |
- **影响**：补发只持续 ~3 秒，正常测量不受影响（用户还没来得及按压时补发已完成）

### 附｜Wi-Fi/BLE 射频竞争导致 HTTP 不稳定
- **现象**：测量期间（BLE 每秒 12 包），电脑远程 HTTP 频繁超时
- **根因**：手机同时跑 BLE + Wi-Fi，2.4GHz 射频拥塞
- **对策**：实测时以手机本地数据为准，电脑只做事后分析（不影响采集）

## 附5：D4 傍晚——"悬空显示 78 BPM" 全案复盘（最终版）

> 这一条要特别记录：过程中出现过两次误判，最终靠**帧缓冲回读**定案。

### 现象
传感器全程悬空、BLE 已连接，手机 App 显示 BPM=78，偶尔变空白；同时 OLED 状态点一直**闪**（"未连接"）。

### 第一次误判（错误结论）
以为是**补发突发的射频串扰**抬高了 p50（实测补发期 p50 确实到 18-20，贴着质量门阈值 18）。
→ 加了"补发期间 p50 门 18→30"，但**问题仍未解决**。

### 第二次误判（测试无效）
按"断连重连"跑了几轮验证，结果显示零假阳性——但用户指出 OLED 点一直在闪。
复查发现：**那几轮根本没连上**（App 的 `connectedState` 是僵尸值，`connect()` 直接 return，扫描都没启动）。
→ 所以那些"验证通过"全部作废。

### 真根因（两处）
1. **App 僵尸连接状态**：刷固件时板子重启，链路已断，但 App 被系统冻结没收到 `onDisconnected` 回调，
   `connectedState` 停留在 true → 之后 `connect()` 早退；界面继续显示断线前的旧值 **78**（这就是"悬空 78"的来源）
2. **固件状态点无日志**：`BLE_GAP_EVENT_DISCONNECT` 不打日志，无法从串口确认断开

### 修复
| 侧 | 改动 |
|---|---|
| App | 加 4 秒数据超时看门狗 `verifyConnection()`；`connect()` 前先自检并清理僵尸；`forceReset()` 强制清 GATT |
| App | 回前台先 `verifyConnection()` 再请求补发 |
| 固件 | 断开事件打 `reason` 日志；UI 行增加 `conn=` 字段（65535=未连接）|

### 定案证据（帧缓冲回读）
```
点区域 行3-7 × 列38-42:
  ..#..      ← 空心环 = 固件认为未连接
  ####.         （conn=65535，与 App 僵尸状态一致）
  #..##
  #..#.
  .###.
```
修复后重新连接：
```
conn 变化: 65535 → 1（切换次数 2，无抖动）
OLED 点: 实心 ✅
App: conn=True
```

### 结论与教训
- **"悬空 78 BPM" 不是算法误报，是 App 显示了断线前的旧值**
- 射频串扰修复（补发期 p50 18→30）保留为防御性措施，实测不影响真实信号（按压时 p50 达 44）
- **诊断顺序应优先用"帧缓冲回读"确认屏幕真实内容**，再推测原因——这次绕了两圈才用上
- 连接状态必须有**看门狗**，不能只依赖系统回调（后台冻结会吞掉回调）

## 附6：D4 晚——两端口径统一 + 运行时调试通道

### 问题｜App 与固件对"是否连接"判断不一致
- **现象**：App 显示已连接、OLED 点闪烁（固件认为未连接）；反之亦然
- **根因**：两边各有一套状态机——固件靠 NimBLE 事件（唯一真值），App 靠 GATT 回调 + 独立标志位
  （回调可能被系统冻结吞掉，标志位就变成"僵尸"）
- **修复**：**App 的"已连接"改为由数据新鲜度推导**（1.5 秒内收到数据才算连），与固件唯一真值对齐
  - 每 500ms 跑一次 `refreshLinkState()`
  - 检测到丢失 → **自动重连**（最多 5 次）
- **验证**：连续 12 次双端对比，除首次因 1.5s 判据滞后外全部一致；断线后 6 秒自动恢复

### 改进｜调试代码驻留板子（不再靠反复烧录）
固件新增**运行时配置 + 命令通道**（写入 FFE4 特征，文本 `C:` 前缀）：

| 命令 | 作用 |
|---|---|
| `?` | 打印当前配置 |
| `thr 42` | 峰检测阈值 |
| `gap 350` | 最小峰间距(ms) |
| `q 18 45` | 质量门 p50/p95 |
| `dbg 0\|1` | UI/TRK 日志开关 |
| `dump 0\|1` | 帧缓冲回读开关（省串口带宽） |
| `mode 0\|1\|2` | 跟踪器：关/接管/影子 |

## 附7：D4 晚——连接稳定性排查（三个真凶）

> 这一轮把"莫名断连"彻底查清，其中**两个是我自己的调试行为造成的**。

### 真凶 1｜串口监听会复位板子（最隐蔽）
- **现象**：每次我打开 COM6 监控，板子就重启、BLE 断开
- **证据**：串口里出现 `rst:0x15 (USB_UART_CHIP_RESET)` 启动横幅
- **根因**：pyserial 默认在 `open()` 时拉 DTR/RTS，ESP32-C3 原生 USB 会把它当复位信号
- **修复**：
  ```python
  ser = serial.Serial()
  ser.port='COM6'; ser.baudrate=115200
  ser.dtr=False; ser.rts=False     # ← 必须在 open() 之前设置
  ser.open()
  ```
- **验证**：改后 8 秒内零启动横幅
- **教训**：**今天下午绝大多数"断连/僵尸状态"都是我自己造成的**

### 真凶 2｜重复连接抢占唯一的连接位
- **现象**：App 日志同一秒出现两条"已连接"，随后断开
- **根因**：扫描泄漏导致 `onDeviceFound` 触发两次 → 两个 GATT 实例；板子最多 1 个连接
- **修复**：
  - GATT 回调加实例校验（`btGatt !== gatt` 的回调直接忽略）
  - 连接加互斥标志 `connecting`，15 秒超时自动释放

## 附8：D4 晚——"恒定 78 BPM" 伪影（用户发现，最重要的一个 bug）

### 现象（用户提出质疑）
- 每次测量都显示 **78 BPM**，几乎不变（σ=0.6）
- 同刻手表读数是 **70/76**（波动 74~78）——对不上
- 用户判断："今天每次都是 78，这不对吧"

### 根因（数据判决）
录原始波形离线复算：
```
峰数 64 / 25.2 秒 = 2.54 峰/秒
i+1 间隔中位 = 365ms  ← 紧贴不应期 350ms
76% 的间隔落在 350~420ms
CV = 0.17（干净脉搏应 <0.10）
```
**结论：信号弱时，噪声峰在 350ms 不应期一到就被检出，
间隔 ≈ 不应期长度 → 输出 = 60000/(2×365) ≈ 82 → 稳定在 78。
输出测的是"算法自己的不应期"，不是心率。**

### 判别标准的确定（对照实验）
| 数据 | CV | p50 | p95 | 是否真实 |
|---|---|---|---|---|
| ★历史最佳会话（真值 78.9）| **0.020** | 60 | 150 | ✅ 真实 |
| 胶带固定（好耦合）| — | — | — | ✅ |
| 本次弱信号（显示 78）| **0.17** | 34 | 76 | ❌ 噪声触发 |

→ **间隔变异系数 CV 是干净判别器**（与"是否贴不应期"无关：好数据也 100% 贴，但 CV=0.02）

### 修复
`get_bpm()` 增加间隔规律性校验：
```c
float cv = sqrtf(var) / mean;
if (cv > 0.12f) return 0;   // 间隔不规律 → 噪声触发，不出数
```
UI 行同时输出 `cv=` 便于现场判读。

### 验证（同刻对照）
| 时间窗 | 手表 | 本设备 | 误差 |
|---|---|---|---|
| 16:30:50~16:31:15 | **76（74~78）** | **75（72~79）** | **1 BPM** ✅ |

且修复后读数不再恒定：72~79 自然波动，CV 0.04~0.11，出数率 46/49。

### 教训
1. **"太稳定"本身就是异常信号**——真实生理量必有波动，σ≈0 要警惕
2. 算法参数（不应期）会**伪装成测量结果**——输出恰好等于参数倒数时，务必怀疑
3. 用户的一次直觉质疑，抵得上十次自动化测试

## 附10：冷启动保护 + 最终同刻对照（0 BPM 误差）

### 问题｜OLED 偶尔空一下然后跳到 78
- **现象**：重启/刚连接后先出现 `---`，然后突然显示 78，按一会儿恢复正常波动
- **根因**：冷启动时间隔窗口只有 3 个样本，CV 统计不可靠 → 可能偶然放行伪影值
- **修复**：**要求至少 5 个间隔 + 连续 4 帧（2 秒）通过 CV 校验才输出**
  - 首次出数延迟到 ~3.5 秒
  - 重启后不再出现瞬态假值（复位实测：0,0,0,0,0,0,0,[3.5s]78,78,...）

### 最终同刻对照（决定性验证）
| 时间窗 | 手表 | 本机 | 误差 |
|---|---|---|---|
| 16:30:50~16:31:15 | 76（74~78） | 75（72~79） | **1 BPM** |
| 16:39:17~16:39:46 | **78（75~79，前段76后段升）** | **78（均值77.2，69~79）** | **0 BPM** |

**两侧连趋势都同步**：都呈现"前段 76 → 后段 78~79 上升"。
→ 证明跟踪的是同一真实生理过程

### "恒定 78" 的最终定性
| 阶段 | 现象 | 性质 |
|---|---|---|
| 轻按（信号弱） | 恒 78、CV=0.17 | ❌ 不应期伪影（已修复） |
| 按实（信号好） | 78 附近小幅波动、CV=0.03 | ✅ 真实测量（用户静息心率就在 76~78） |

两件事叠加才造成"每次都 78"的错觉。**修复后系统既能测准（0-1 BPM），也能诚实拒测（弱信号/CV 异常时不出数）。**

### 当前出厂固件的完整判据链
```
峰检测(阈值40/间距350ms) → 质量门(p50>=18, p95>=45, 滞回)
→ 隔峰 i+2 间隔 → 合理性过滤(±30%)

```

## 附11：D4 深夜——跑步数据解算（TROIKA 式谱分析）

### 数据
两组慢跑（串行采集、同一设备、传感器未固定）：
| 会话 | 被试 | 时长 | 波形 | IMU |
|---|---|---|---|---|
| #4 | 赵国宇 (180cm/61kg) | 188s | 38200 点 | 9872 样本 |
| #5 | 张祥 (173cm/63kg) | 107s | 10700 点 | 5012 样本 |

### 方法
1. **TROIKA 式谱峰跟踪**（Zhang et al. 2014, IEEE TBME）：带通 0.5-4Hz → FFT → 候选峰 → 用 IMU 步频排除 → 谱峰跟踪
2. **自相关**（1-4Hz 带通后）交叉验证

### 结果
| 会话 | 自相关基频 | 二次谐波 | IMU 步频 | 设备显示（旧） | 设备（修复时基后） |
|---|---|---|---|---|---|
| #4 | **80-81 BPM** | 162-167 | 172-174 | 78 | 81 |
| #5 | **92 BPM** | 184 | 192-209 | 78 | 82 |

### 三个结论
1. **跑步时压电基频 = 真实心率**（80/92），二次谐波约两倍
2. **步频与基频、谐波都不同频** → 步态直接耦合不成立（互相关 r≈0.2 也支持）
3. **"78 是伪影"的假设被否**：两位被试确实心率 80-92，设备偏差 3-14 BPM 来自 i+2 配对

### 遗留
- i+2 配对仍有系统性偏差（±10%），需用自相关/模板做独立校验
- 数据表导出要求：**对齐时间轴 + 北京时间 + 可关联天气**（待做）
- 传感器未固定导致运动伪迹偏大，绑定后需重采
