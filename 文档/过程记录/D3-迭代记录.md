# 第一部分 · D2：测量方法、耦合与物理

## 一、算法

### 问题 1｜旧检测器在真实波形上"架构性失明"
- **现象**：包络状态机（PulseV2）在一轮连续双峰波形上输出 **0 拍**，而同一份数据人工看明明有脉搏
- **定位**：把历史数据全部重放 → 旧引擎在多峰/双峰结构上会一直卡在"等回到基线"的状态
- **解决**：换成**峰普查法**——dev 阈值 40 + 最小间距 350ms + **隔峰中值**（跳一个峰取间隔，免疫双峰）
- **结果**：同一份数据 **0 拍 → 82 峰**；全部历史"废数据"重析后信号都在

### 问题 2｜双峰到底是机械振铃还是生理信号？
- **现象**：每拍有两个峰，间距 ~360ms，若为振铃则测周期的方法全错
- **判决实验**：刚性板+质量加载，改变系统共振频率
- **结果**：**间距 360→365ms 纹丝不动** → 不是机械振铃，是**生理重搏波** → 隔峰配对成立

### 问题 3｜心率对比出现"82 vs 68"的自相矛盾
- **根因**：两次测量不是同刻——等长收缩升压后放松回落，生理状态已经变了
- **解决**：改为**同刻对照**（手表 ECG 与本机同时读数）
- **结果**：跨 2 名受试者、多位置，误差 **±2 BPM**（最好一轮 **−0.2**）

### 问题 4｜整轮误差 −9.4 BPM（表带压顶轮）
- **根因**：一段测量里既有好耦合段也有弱耦合段，整轮平均被垃圾段拖坏
- **解决**：**分段质量门控**（按 p95/状态把段切开，只统计好段）
- **结果**：同一轮 −9.4 → **−0.2**；并确认"全程弱档不可救"

| 问题 | 定位 | 解决 / 结论 | 结果 |

# 第二部分 · D3：通信、波形质量、显示与 App

## 四、通信（BLE 全链路）

### 问题 5｜手机扫不到设备
- **定位**：PC 用独立 BLE 栈扫也扫不到 → 先排除 App 代码
- **根因 A**：Android 12+ `BLUETOOTH_SCAN` 未声明 `neverForLocation`，系统直接过滤扫描结果
- **根因 B**：用系统级"设备名过滤"，对广播包格式过于敏感
- **解决**：加 `neverForLocation`；无过滤扫描 + 手工匹配（名字/服务 UUID）；半程无果自动重启扫描
- **结果**：PC 与手机均稳定发现 `CYBER-PULSE`（−63 dBm）

### 问题 6｜广播包超长，板子其实没广播
- **定位**：Flags(3)+名字(13)+128位UUID(18)=**34 B > 31 B 上限**
- **根因**：`ble_gap_adv_set_fields` 失败但返回码没检查
- **解决**：UUID 移到 **scan response**，主包只留 16 B；所有 NimBLE 调用打印返回码
- **结果**：广播日志正常，可被 PC/手机发现

### 问题 7｜连上瞬间就断、"找不到脉搏服务"
- **定位**：板子日志显示"连接成功且已在发通知"，说明卡在**服务枚举**
- **根因 A（固件）**：GATT 服务表写在 `on_sync()` **栈上**，NimBLE 只存指针 → 函数返回即失效
- **根因 B（App）**：`requestMtu()` 与 `discoverServices()` 并发 → 服务发现返回空表
- **解决**：服务表改**文件级 `static const`**；App 改为"先发现→订阅→再协商 MTU"，发现失败重试 2 次
- **结果**：PC 可完整枚举 `FFE0/FFE1/FFE2`；App 订阅成功、MTU=512、波形流正常

### 问题 8｜连过一次后谁都扫不到
- **定位**：板子一直发通知 → 它认为还连着 → 停止广播
- **根因**：App 发现失败不断开，连接悬挂
- **解决**：失败路径强制 `disconnect+close`，重连前清理旧连接
- **结果**：可反复连接/断开

### 问题 9｜手机后台 2 秒掉线、调试页面失联
- **定位**：`adb shell am start` 拉回前台，HTTP 立刻恢复 → 系统冻结后台进程
- **解决**：App 启动即开调试服务、测量页常亮、电池优化白名单入口
- **结果**：前台稳定（后台仍需系统"省电策略=无限制"）

## 五、波形质量（假阳性攻坚）

### 问题 10｜悬空薄膜会"跳数字"
- **数据**：录 120 秒悬空原始波形复算 → **118/120 秒都在输出约 67 BPM**
- **根因**：`get_bpm()` 只看有没有峰，不看质量；噪声尖峰间隔恰好落入 500~1400ms
- **解决**：质量门 `p95 ≥ 45 且 p50 ≥ 18`（悬空 p50 8~12；贴肤 p50 42~62）
- **结果**：假 BPM **118 秒 → 0 秒**；好信号复算不受影响

### 问题 11｜加了质量门后 BPM 变空、掉到 56
- **根因**：门加在**峰值检测**里 → 丢峰 → 隔峰配对断链 → 配对错位算出 56
- **解决**：检测自由、**只在输出端门控**；窗口 7→9；偏差 >30% 的间隔不入窗
- **结果**：中途掉零 **0 次**；BPM **76~78、σ=0.7**（此前 σ=6.1 且带 58 跳变）

### 问题 12｜GOOD/WEAK 状态来回漂
- **根因**：p95 在阈值 52 附近徘徊 + 状态无平滑
- **解决**：状态"质量优先" + p95 平滑（τ≈2s）
- **结果**：GOOD 占比 **91%~100%**

### 新增｜实时波形流
`FFE2` 特征，1kHz 抽 10 → **100Hz**，每 100ms 发 10 个 int16；App 5 秒滚动平滑曲线

## 六、显示与硬件

### 问题 13｜OLED 偶发卡住
- **定位**：固件加三个探针（显存整帧 ASCII 回读 + 主循环滞后 + 刷屏失败计数）
- **探针结论**：显存内容正确且每帧都在变、`oled_fail=0`、主循环最大滞后 55ms
- **根因**：BLE 通知在**主循环同步发送**，NimBLE 抢锁阻塞 ADC 与刷屏
- **解决**：通知入队 + 独立 `ble_tx` 任务（队列满即丢）
- **结果**：滞后 ≈55ms、刷屏失败 0、堆稳定 183 KB

## 七、App 与数据

| 问题 | 根因 | 解决 | 结果 |
|---|---|---|---|
| `POST /session` 报 body 非法 | NanoHTTPD 不解析 `application/json` | 按 content-length 自读输入流 | 建会话/改配置恢复正常 |
| 标注字段不够 | 表单写死 | 表单改 **config.json 驱动**（姓名/学号/性别/左右手/手指/温湿度/备注） | 电脑可远程改字段 |
| 不能远程调试 | 只能手点 | 开发者 HTTP：连蓝牙、建会话、开停记录、导出、看波形 | 全流程可远程驱动 |

**端到端验证**：远程建会话 → 按压 20 秒 → 入库 **79 条**（平均 512ms/条，无断档）→ CSV + manifest 导出正常。

# 第四部分 · D4 起：持续迭代（影子模式与算法演进）

## 一、老方法加固（先保证不退化）

### 问题｜BPM 偶发 `-1`
- **现象**：恢复老方法后，悬空/弱信号时 BPM 显示 `-1`
- **根因**：`intervals[]` 是固定 9 长度的环形数组，新间隔插在**尾部**，取值却复制**前 n_iv 个**；
  前期有效区间少时复制到的全是初始 0 → `60000 / 0` → 未定义行为
- **解决**：一律取尾部 `intervals + (BPM_MED_N - n_iv)`
- **结果**：悬空 10s 全程 `bpm=0`；按压 23s **恒 78、σ=0.0、GOOD 93%**（历史最佳）

## 二、算法演进（不改出厂行为）

### 决策｜新算法只做影子
- 老路径（thr 40 / 350ms 间距 / 隔峰 i+2 / 合理性过滤 / 质量门）**一行不动**，继续驱动 OLED 与 BLE
- 新算法（模板匹配 + 卡尔曼）在影子通道并行计算，结果走 `bpm2`/`sc` 字段
- 编译开关：`USE_TRACKER = 0(关) / 1(接管) / 2(影子)`

### 问题｜模板搜索太重
- **实测**：每次 21ms（15 个候选）→ 降到 11 个候选后 **15.6ms/次**
- **影响**：每 500ms 一次 ≈ 3% CPU；主循环滞后常态 55ms，每 5s 有一次 ~200ms 尖峰（来自调试用显存回读，正式演示关闭）
- **解决**：候选数 15→11；调试打印在发布版关闭
- **结果**：堆稳定 178KB，无泄漏

### 关键数据｜为什么高心率必须换配对方式
| 场景 | 真拍保留率 | i+2 中位 | 得出 BPM | 真值 |
|---|---|---|---|---|
| 理想 80 | 102% | 1120ms | 54 | 80 |
| 理想 150 | 100% | 800ms | **75** | 150 |
| 纹波 150 | 100% | 800ms | **75** | 150 |

- 形态校验能把伪峰挡掉（保留率≈100%），**但救不了配对**：心率高时重搏波与主峰融合，i+2 跨两拍 → 半值
- 结论：**峰检测=触发、模板=形态校验、动态配对+卡尔曼=测时**，三层缺一不可

### 设计｜四级演进路线（全部写进《跑步模式-心率跟踪设计.md》）
1. 固定阈值 + i+2 中值（出厂，已验证）
2. SNR 自适应阈值 + 相位锁定 + 卡尔曼（仿真中，高心率仍不稳）
3. 协方差导出的搜索窗口（σ 含速度项）+ 绝对伪迹门（原理正确）
4. **贝叶斯融合**：先验=KF 预测，似然=幅度×NCC 形态，后验 argmax；R 由后验曲率自动得出

### 落地｜两条 Kimi 建议已实现（影子通道内）
| 建议 | 实现 | 说明 |
|---|---|---|
| R 随信号质量变化（SQI） | `R = 波形噪声 + 25(1−sc)² + 12(1−p95/120)²` | 形态差/耦合弱 → 更不信测量 |
| 模式自适应 Q | `σ_a = 1.5 + 2.5·min(1, |v|/5)` | 无 IMU 时用自身速度当模式代理 |

日志已输出 `TRK|old= new= sc= R= sa= cost=`，明天跑动数据的每一次更新都能复盘。

## 三、数据资产

### 问题｜老录音不能当真值
- **做法**：`curate_data.py` 六条规则筛全部会话（排除坏样本 / 有信号 / 搏动结构 / 周期性可信 / 模板能量集中 / 历史一致性）

- **结论**：老数据是固件迭代期产物，不能给运动算法做真值；必须用新硬件重录后同规则复筛
