# 闪存数据导出 · 操作说明

> 本文档固化"从设备闪存把原始波形拿回电脑"的最终可行方案。
> 目标读者：明天的我 / 队友。

---

## 一、结论先行

```
设备端：控制台改 USB 独占 + rec stream（十六进制文本流式导出）
电脑端：python tools/pull_hex.py --port COM6 --index N --out recNNN.raw
```

600 KB 的文件约 10~20 秒拉完，字节精确、块数完整。

---

## 二、为什么不能用普通方式（三条根因，别再踩）

| # | 坑 | 现象 | 真相 |
|---|---|---|---|
| 1 | **主控制台是 UART0** | 响应很慢、呈 4 KB 突发 | `CONFIG_ESP_CONSOLE_UART_DEFAULT=y`，所有输出要等 UART0 以 115200 排空（GPIO20/21 根本没接） |
| 2 | **stdio 缓冲** | 命令发出很久才有回应 | 4 KB 缓冲，`fflush` 也不一定立刻出 |
| 3 | **行尾转换** | 二进制帧 CRC 大量失败 | 控制台把 `0x0A` 转成 `0x0D 0x0A`，1256 帧里 435 帧被撑坏 |

**第 3 条最致命**：任何二进制协议（包括带 CRC 的自定义帧）都会被静默破坏，
而且只在某些字节出现时才坏，看起来像"随机丢包"。

## 三、设备端配置（已固化在固件里）

`main.c` 的 `app_main()` 开头：

```c
setvbuf(stdout, NULL, _IONBF, 0);
usb_serial_jtag_vfs_set_tx_line_endings(ESP_LINE_ENDINGS_LF);
usb_serial_jtag_vfs_set_rx_line_endings(ESP_LINE_ENDINGS_LF);
```

`sdkconfig`：

```
CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y
# CONFIG_ESP_CONSOLE_UART_DEFAULT is not set
CONFIG_ESP_CONSOLE_SECONDARY_NONE=y
```

> 注意：行尾设置在这颗芯片上没有完全生效（控制台层仍会转换），
> 所以**导出协议最终选择了纯 ASCII 的十六进制文本**，从根上绕开。

---

## 四、导出协议（十六进制文本）

```
设备 → 电脑：

STREAM|START
<文件字节数>
F<seq>,<len>,<hex>      ← 每块 512 字节，hex 为小写十六进制
F<seq>,<len>,<hex>
...
STREAM|END
```

- 每行长度约 1 KB，纯 ASCII，不受行尾转换影响
- `seq` 从 0 递增，电脑按 seq 重组
- 块内容 = 文件原始字节（含 16 字节文件头）

### 文件格式（重组后）

```
[16B 头]  "CPLS" ver fs(2B) start_ms(4B) task_id(4B)
[数据块]  ts_ms(4B) + n(2B) + n×int16
```

- `fs` 标称 1000（实测 1001~1003）
- `task_id` = 手机会话号，用于和 App 数据配对

## 五、操作步骤

### 1. 确认端口

```powershell
[System.IO.Ports.SerialPort]::GetPortNames()
```

### 2. 查看文件列表

```bash
python tools/pull_hex.py --port COM6 --index 1 --list
```

（若没有 `--list`，直接看串口输出的 `文件:` 行）

### 3. 导出

```bash
python tools/pull_hex.py --port COM6 --index 4 --out ../数据-闪存/rec004.raw
```

输出示例：

```
文件 642966 字节，共 1256 块，接收中…
  699/1256 块
OK rec004.raw：642966/642966 字节，1256/1256 块
   头: b'CPLS' ver=2 起始=211850ms 任务号=6
```

### 4. 校验

- `OK` 且字节数一致 → 完成
- `PART` → 重跑一次（脚本会重新从头发，不会损坏已有文件）

## 六、脚本参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `--port` | COM6 | 串口号 |
| `--index` | 必填 | recNNN 的 NNN |
| `--out` | 必填 | 输出 .raw 路径 |
| `--list` | 关 | 只列文件不导出 |

脚本内部：
- 打开串口前设 `dtr=False, rts=False`（否则板子会被复位）
- 先发 `dump 0 / raw 0 / dbg 0` 关闭周期性日志
- 启动流最多重试 12 次（命令可能偶尔丢失）

---

## 七、排障

| 现象 | 原因 | 处理 |
|---|---|---|
| `启动失败` | 命令没被接收 / 设备在跑别的 | 重跑；或拔插 USB |
| 收到 0 字节 | 设备卡死（旧固件）| 按板子 RST |
| 字节数对但块数少 | 行被截断 | 重跑一次 |
| `PermissionError` | 串口被占用 | 关掉其他串口工具 / 杀残留 python |
| 导出后设备无响应 | 流式导出期间禁止其他命令 | 导出完会自动 `rec close`，重连即可 |

## 八、历史方案（保留但不再使用）

| 工具 | 为什么弃用 |
|---|---|
| `fetch_flash.py` | 逐块请求，应答率仅 25%，600 KB 要 10 分钟 |
| `fetch_fast.py` | 流水线请求，仍受行尾转换影响 |
| `stream_pull.py` | 二进制流式，帧被 `0x0A` 转换破坏 |
| `pull_file.py` | 二进制流 + 补洞，同样受转换影响 |

> 保留是为了记录踩坑过程；**实际只用 `pull_hex.py`**。
